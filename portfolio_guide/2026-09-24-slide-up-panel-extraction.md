# 2026-09-24 - About becomes a card; shared SlideUpPanel extracted

## The "Why" (Design Decisions)

About was a `/about` page as of a few hours earlier the same day. The user reversed that: About should be a slide-up glass card identical in behavior to Contact, triggered from the same Hero button, with both cards visually larger and sitting further from the bottom-right corner than the original compact 360px widget.

**Extraction over duplication.** `ContactCard.jsx` used to bundle its trigger button, its open/close/focus/mount-timing state machine, and its content all in one file. Needing a second card meant either copy-pasting the state machine (the genuinely fiddly part - transition timing, focus management, Escape, reduced-motion) or extracting it once. Two real call sites is exactly the point where that extraction pays for itself rather than being speculative.

**Mutual exclusion, added beyond the literal request.** At the new, much larger size, two independently-managed panels could both be open and visually overlapping. `SlideUpPanel` was made a *controlled* component (`isOpen` owned by the parent) specifically so `Hero.jsx` could hold one `openPanel` state and make opening either card close the other for free.

## Core Concepts (the debugging story - two real bugs found via actual browser testing, not just eyeballing)

**Bug 1: a full-screen invisible "click outside to close" div silently ate clicks meant for other buttons.** The original Contact card used a `position: fixed; inset: 0` scrim div purely to catch outside clicks - it had no visual dimming, so it was easy to forget it still fully occupied the click hit-testing layer above everything else on the page. The instant a second card's trigger button needed to be clickable *while the first card was open* (to satisfy mutual exclusion), this broke: the scrim, sitting at a higher z-index than Hero's own content, intercepted the click before it ever reached the About button underneath. This is the kind of bug that's invisible until you actually test the specific interaction (clicking a different trigger while a panel is open) rather than just testing each panel in isolation - which is exactly why this was only caught by scripting the actual click sequence in a real browser rather than trusting the design on paper. Fixed by removing the div entirely and switching to a `document`-level `mousedown` listener that checks `!panelElement.contains(event.target)` - a listener observes, it doesn't intercept, so the click still reaches whatever's underneath it.

**Bug 2: `onTransitionEnd`-driven unmounting was flaky specifically in the multi-panel, canvas-heavy scenario.** The closing side of the animation waited for a native `transitionend` DOM event to actually unmount the panel from the tree. In isolated testing this worked fine, but running the full open → switch-to-other-panel → close sequence repeatedly showed it intermittently getting stuck: a panel would correctly animate its `transform` back to closed but never actually unmount, leaving an invisible, fully-functional-but-should-be-gone panel sitting in the DOM. The most likely cause: `transitionend` reliably bubbling up through a *portaled* subtree, on an element with `backdrop-filter: blur()`, sitting on top of a *continuously re-rendering* WebGL canvas, under real GPU/compositor load, is exactly the kind of environment where a browser's transition-completion event can be delayed or occasionally dropped - and this is more a property of the actual rendering conditions than of React state logic, so it's not something a code read-through would have caught. Fixed by replacing the event-driven unmount with a fixed `setTimeout` matched to the CSS transition's declared duration (`320ms`, called out as a magic number that must be kept in sync with `index.css` in both places). A timer firing at a fixed delay doesn't depend on the browser successfully detecting and dispatching a completion event at all - strictly more robust for this specific combination of portals + blur + a perpetually-animating background, at the cost of one small hardcoded coupling between a JS constant and a CSS value.

Both bugs were found by scripting the actual interaction sequence (open, switch panels, check DOM state, repeat several times) against a running dev server rather than by reading the code and reasoning it should work - repeated real testing surfaced a specific flake rate the first isolated test missed entirely.

## Implementation Breakdown

- `client/src/components/common/SlideUpPanel.jsx` - the extracted shell: `isMounted` (DOM presence, driven by a fixed-timer close instead of `transitionend`) and `isEntered` (drives the open transform, via the same double-`requestAnimationFrame` entrance trick as before) are tracked as two distinct pieces of state rather than reusing the `isOpen` prop name directly, because becoming a controlled component means "mounted" and "entered" can no longer be assumed to land in the same render commit the way they could when the same component managed its own click handler synchronously.
- `client/src/components/contact/ContactCard.jsx` - reduced to content only (photo/header/phone/email rows); the phone-digit-reassembly effect now runs on plain mount rather than being keyed to an `isOpen` prop, since the component only ever mounts while its panel is actually open.
- `client/src/components/about/AboutCard.jsx` (new) - the same heading + paragraph that used to live in the deleted `About.jsx` section component / `AboutPage.jsx` route.
- `client/src/components/sections/Hero.jsx` - owns `openPanel` state (`'about' | 'contact' | null`) and both trigger `<button>`s (previously Contact rendered its own trigger; About's was a `<Link to="/about">`). Renders two `<SlideUpPanel>` instances with `AboutCard`/`ContactCard` as children.
- `client/src/App.jsx` - the `/about` route is gone; only `/` and `/projects` remain.
- `client/src/index.css` - the shared structural classes were renamed from `.contact-*` to `.slide-panel*` (the content-specific `.contact-card__*` classes stayed, since they're still Contact-specific); `.slide-panel` grew from `max-width: 360px` / `right`/`bottom: 24px` to `max-width: 520px` / `right`/`bottom: 56px`, with the closed-state `translateY` offset and `max-height` calc adjusted to match.
